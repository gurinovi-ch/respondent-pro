# Привязка планшета к Компании — pairing-код → device API-key

Дата: 2026-10-02. Статус: дизайн утверждён пользователем (02.10.2026).
Репозитории: клиент — этот repo (Android); сервер — `C:\Users\leonb\OneDrive\Документы\Default Project\server` (NestJS + Prisma, база наработки RESPO.SERVER).

## 1. Контекст и цель

Кабинет `my.respondent.pro` (Comпания/организации) уже умеет: регистрация планшетов (`POST /api/tablets`, admin JWT), генерация и ротация API-ключей (`rpro_*`), приём отзывов (`POST /api/feedbacks`, `X-API-Key`), релей отзывов в Telegram. Нет механизма, которым планшет **получает** свой ключ и связывается с Компанией.

Цель этапа: самый безопасный И самый простой способ привязки — одноразовый pairing-код → собственный API-key планшета. Пароль/логин человека на устройство не попадает никогда.

## 2. Область

**В scope:**
- Сервер: генерация pairing-кода (admin), обмен кода на ключ (`POST /api/pair`), новая таблица `PairingCode`, поле `Tablet.pointName`.
- Клиент: секция «Кабинет» в Настройках (ввод кода, статус привязки, отвязка), зашифрованное хранение ключа, HTTP-клиент с `X-API-Key`.
- Поведение при отзыве ключа (HTTP 401) → сброс в состояние «не привязан».

**Out of scope (отдельные этапы):**
- Забор настроек/контента из кабинета (GET), heartbeat/мониторинг (`lastSeenAt`), отправка отзывов через сервер вместо Telegram, справочник Точек с аналитикой, переименование Точки с планшета, QR-ввод pairing-кода, device-meta (модель/версия APK) в heartbeat.

## 3. Утверждённые решения

1. **Точка (v1):** свободное поле `Tablet.pointName`, заполняется и правится только в кабинете; планшет отображает. История отзывов не зависит от имени (связь через `tabletId`); полноценный справочник Point — позже.
2. **Ввод кода:** только текстом (камеру не возвращаем — CAMERA в манифесте `tools:node="remove"`).
3. **Отзыв ключа:** при явном HTTP 401/403 от сервера на авторизованных запросах — очистить локальный ключ, показать статус-строку «Привязка отменена». Не диалог. Сетевые ошибки (timeout, 5xx) отвязкой НЕ считаются.

## 4. Флоу

```
Кабинет (браузер):  «Добавить планшет» (имя + Точка)
                    → запись Tablet + ApiKey rpro_* (существующее поведение)
                    → «Получить код привязки» → одноразовый код, TTL 15 мин
Планшет:            Настройки (PIN) → «Кабинет» → ввод кода → «Привязать»
Сервер:             POST /api/pair { code } → проверки → выдаёт текущий
                    активный ApiKey планшета + org/point meta
Планшет:            сохраняет ключ (EncryptedSharedPreferences) → «привязан»
Отзыв:              в кабинете rotate-key/delete → следующий запрос 401
                    → планшет: локальная очистка, статус «не привязан»
```

Ключ коду не содержит: при успехе выдаётся **текущий** активный ключ Tablet → ротация ключа после выдачи кода не ломает (код доставит уже новый ключ).

## 5. Контракт API

### Существующие (без изменений, кроме pointName)

| Method | Endpoint | Auth | Изменение |
|---|---|---|---|
| POST | `/api/tablets` | Bearer | `body.pointName?` — новое опциональное поле |
| PUT | `/api/tablets/:id` | Bearer | принимает `pointName?` |
| POST | `/api/tablets/:id/rotate-key` | Bearer | без изменений |
| POST | `/api/feedbacks` | X-API-Key | без изменений |

### Новые

**`POST /api/tablets/:id/pairing-code`** (Bearer, admin) → 200 `{ code, expiresAt }`
- Один активный код на планшет (upsert): старый инвалидируется.
- Формат: 8 символов из безамбигуального алфавита (`2-9A-Z` без `I O`), отображение `XXXX-XXXX` (на вход нормализуется).
- TTL 15 минут.
- В ответе — код в открытом виде (его видит только авторизованный админ и вводит руками); в БД только SHA-256 хэш (с верхним регистром без дефиса).

**`POST /api/pair`** (без auth, throttler) — body `{ code: string }`
- Проверки: хэш-совпадение → не просрочен → не использован.
- Rate limit: 10 запросов/мин на IP (`@nestjs/throttler`), иначе 429 — суммарно ≤150 попыток за жизнь кода против ~32^8 комбинаций (счётчик попыток на код не применяется: сервер находит код только по хэшу, и при угадывании строка не находится — TTL + rate-limit закрывают перебор).
- Успех → 200 `{ apiKey, tabletId, organizationId, organizationName, pointName }`; `usedAt` выставляется (код одноразовый).
- Любая неудача (неверен, просрочен, использован) → **одинаковый** ответ 400 `{ message: "invalid or expired code" }` — не раскрывать причину.
- Rate limit: 10 запросов/мин на IP (`@nestjs/throttler`), иначе 429.
- События логируются (level warn: IP, результат) — для диагностики попыток.

### Требования безопасности (сервер)

- Только HTTPS (терминация на `my.respondent.pro`).
- Хэш кода — SHA-256; сами коды одноразовые и короткоживущие — brute-force закрыт суммарно (алфавит ~32^8 × TTL 15 мин × rate-limit 10/мин).
- `ValidationPipe` (whitelist) уже глобален — DTO строго `{ code: string }`.
- Существующее plain-хранение `ApiKey.key` в БД — оставляем как есть (hardening «хэш ключа» — отдельным решением, вне этапа).

## 6. Модель данных (Prisma migration)

```prisma
model PairingCode {
  id        String   @id @default(uuid())
  tabletId  String   @unique      // один активный код на планшет
  tablet    Tablet   @relation(fields: [tabletId], references: [id], onDelete: Cascade)
  codeHash  String
  expiresAt DateTime
  usedAt    DateTime?
  createdAt DateTime @default(now())
  @@map("pairing_codes")
}
```

`Tablet`: + `pointName String?` (маппинг `point_name`).

## 7. Клиент (Android)

- **Секция «Кабинет»** в Настройках (за PIN): статус — «не привязан» / «{организация} · {точка}»; поле ввода кода (авто-верхний регистр, формат `XXXX-XXXX`), кнопка «Привязать»; при привязке — кнопка «Отвязать» (только локальная очистка ключа; серверный revoke — в кабинете).
- **Хранение:** `EncryptedSharedPreferences` (androidx.security:security-crypto) — `apiKey`, `tabletId`, `organizationName`, `pointName`. Room/DataStore не трогаются (правило сессии).
- **HTTP:** `KabinetConfig.BASE_URL = "https://my.respondent.pro/api"`; Retrofit `CabinetApi` + interceptor, подставляющий `X-API-Key` (кроме `pair`). Паттерн — существующий `TelegramApi`.
- **Состояние:** unbound / binding / bound / bindingError; 401/403 → очистка + «Привязка отменена».
- **Строки UI:** только AppStrings (ru+en).
- Привязка НЕ меняет текущие каналы отправки (Telegram/Email продолжают работать) — замена каналов = отдельный этап.

## 8. Тесты

- **Сервер (Jest):** unit `pairing` service — happy path; просрочен; повторное использование; неверный код; rotate-key до погашения (код выдаёт новый ключ); e2e `POST /api/pair` + throttler.
- **Клиент (JUnit):** логика состояний привязки (интерфейс `BindingStorage` + in-memory fake — без Robolectric); нормализация ввода кода; обработка 401 ≠ сетевая ошибка; KioskStringsTest расширен новыми строками.
- **Устройственная проверка** (появится API на сервере): паринг → 401-сценарий через rotate-key. Инструментально; визуал — пользователь.

## 9. Риски и ограничения

- Код видят окружающие в момент показа (TTL 15 мин + одноразовость приемлемы; злонамеренный «внутри компании» — вне модели угроз v1).
- EncryptedSharedPreferences требует API 23+ — приложение minSdk 24 ✓.
- Ключ хранится на устройстве в зашифрованном виде — при физическом взломе root-доступа защита ограничена Keystore (принято).
- v1 без device-meta — кабинет не видит модель/версию до этапа мониторинга.
